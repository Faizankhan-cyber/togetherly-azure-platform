# Togetherly Azure Platform v2.0.0

**Release type:** V2 security and governance milestone
**Certification milestone:** Completed after SC-500  
**Release tag:** `v2.0.0`  
**Tag target:** V2 release commit on `main` after the V2 implementation and documentation updates.  
**Release status:** Git tag `v2.0.0` and published GitHub release are live. V2 implementation, evidence upload, preservation and Azure resource-group teardown are officially complete; the owner confirmed `rg-togetherly-platform` deletion on 2026-11-10.

## Overview

V2 strengthens the V1 VM-hosted Togetherly Workforce application with workload identity, centralized secret storage, Key Vault network restrictions and Azure Policy governance.

## Included

- System-assigned Managed Identity enabled on `vm-togetherly-v1`.
- Azure Key Vault `togetherly-key-2026` using the Azure RBAC permission model.
- Key Vault soft delete with 90-day retention and purge protection.
- VM identity assigned Key Vault Secrets User; authorised operator assigned Key Vault Secrets Officer.
- TinyFish API key stored in Key Vault and retrieved by the Node.js Express API using Azure Identity and Key Vault SDKs.
- TinyFish API key removed from the VM application's `.env` file.
- Key Vault network access restricted to the selected application VNet/subnet and an administrator IP allow-list; `Microsoft.KeyVault` service endpoint enabled on the application subnet.
- Resource-group Project tag policy assignment configured in DoNotEnforce mode.
- Policy compliance scan reported 8 of 8 resources compliant.
- TinyFish Search, Fetch, Agent execution and Agent status workflows re-tested.
- Fourteen V2 screenshot files present in `evidence/v2/`.

## Architecture and scope notes

- V2 extends the existing VM + Nginx + Node.js Express design.
- The TinyFish API listens on loopback port 3001 and is reverse-proxied by Nginx.
- Supabase remains the external application authentication and data service.
- Key Vault uses its public endpoint with network ACL restrictions and a VNet service endpoint. No Private Endpoint was deployed.
- Azure Policy is assigned with DoNotEnforce; it evaluates compliance but does not block resource operations.
- Configuration was performed manually through the Azure Portal.
- GitHub Actions OIDC federation, Azure Functions, Bicep deployment, Sentinel and Log Analytics are not included in V2.

## Verification and evidence

Implementation-time verification included successful VM Managed Identity secret retrieval without printing the secret value, an active TinyFish API systemd service, user-confirmed Search/Fetch/Agent workflow tests, and an Azure Policy compliance result of 8/8.

All 14 screenshot files are uploaded in `evidence/v2/`; the screenshot upload deliverable is complete. Full-size visual review for readability and privacy redactions remains an optional evidence-quality check and is not represented as an independent audit.

## Security and operational limitations

- The Key Vault endpoint is public and restricted by network ACLs; it is not a Private Endpoint.
- The administrator IP allow-list may need updating if the public IP changes.
- Key Vault Secrets Officer is a powerful role and should remain limited to the authorised operator.
- The DoNotEnforce tag policy is not a blocking preventive control.
- Inherited subscription-level Owner assignments were not changed.
- The live VM state, retained disk/public IP costs, and current Azure Cost Management actuals/forecast must be checked in the subscription. This release makes no claim about current charges or remaining student credits.
- This is a learning-project release, not a formal security audit, penetration test or compliance attestation.
