## Implementation and security notes

- The Togetherly Workforce source remains in its separate repository; only the production build was deployed on the VM.
- Nginx served the frontend and proxied `/api/tinyfish/*` to `http://127.0.0.1:3001`.
- The API was shown listening on loopback in the service-status evidence. Do not expose port 3001 through the NSG.
- Server-side environment values were stored in a permission-restricted `.env` file on the VM and excluded from Git; live file permissions were not independently rechecked during closure.
- Supabase remained external. No production database, policy or authentication changes were made for this deployment.
- Azure Functions, its storage account and Key Vault were not deployed.
- Keep `TINYFISH_API_KEY` server-side only.

## V1 security review scope

The screenshot-based review confirms the documented NSG inbound rules: SSH was restricted to a single `/32` source, HTTP and HTTPS were allowed, and the default inbound deny rule was present. The VM network screenshot showed the NSG associated with the VM NIC. The service screenshot showed the TinyFish API listening on `127.0.0.1:3001`.

This is a basic project-level configuration review, not a full security audit or penetration test. Because the VM has since been deallocated, the following host-level settings were not independently rechecked during closure: SSH daemon hardening, UFW state, pending OS security updates, live `.env` permissions, and current certificate validity. They are recorded as **not rechecked**, not as verified controls. No additional hardening work is required to document the completed V1 baseline, but do not claim these checks passed.
