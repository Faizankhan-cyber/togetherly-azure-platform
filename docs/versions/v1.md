# V1 — Initial Azure Deployment

**Status:** Planning  
**Learning alignment:** AZ-900  
**Infrastructure method:** Manual creation through the Azure Portal  
**Target:** Host the Togetherly Workforce frontend on an Azure Linux VM and host its TinyFish API routes on Azure Functions.

## V1 architecture

See [V1 Architecture Diagram](../architecture/v1-architecture.md).

The proposed request path is:

```text
Browser
  |
  | HTTPS
  v
Azure Public IP / DNS
  |
Network Security Group
  |
Linux VM running Nginx
  |                         |
  | static assets           | /api/tinyfish/*
  v                         v
React/Vite frontend     Azure Function App
                              |
                       +------+------+
                       |             |
                    Supabase      TinyFish
```

The existing TinyFish API handlers use the Vercel serverless request/response model. They must be adapted and tested for Azure Functions Node.js v4. There is no existing Express server or conventional Node.js API process to run on the VM.

## Infrastructure approach

- Create all V1 Azure resources manually through the Azure Portal.
- Use one shared resource group: `rg-togetherly-platform`.
- Do not use Terraform or Bicep to provision V1.
- V2 is planned to introduce Azure Bicep as the Infrastructure as Code learning milestone.
- Do not create resources until subscription, region, availability, network exposure, and cost checks are complete.

## Planned V1 resources

- Resource Group: `rg-togetherly-platform` (shared across V1–V5)
- Virtual Network and subnet
- Network Security Group
- Public IP address
- Ubuntu Linux Virtual Machine
- Nginx web server
- Azure Function App using a suitable Node.js v4 hosting configuration
- Storage account required by the Functions hosting configuration
- HTTPS configuration and DNS plan

The exact region, VM size, Functions hosting plan, storage redundancy, DNS option, and TLS approach remain subject to availability, compatibility, and cost validation.

## Application integration requirements

- Deploy a pinned Togetherly Workforce frontend build to the VM.
- Configure Nginx to serve static files and proxy only the required `/api/tinyfish/*` routes to Azure Functions over HTTPS.
- Adapt the existing Vercel handlers to Azure Functions while preserving authentication, active employee and role checks, URL validation, HTTP methods, status codes, and response behaviour.
- Keep `TINYFISH_API_KEY` server-side only.
- Keep Supabase as the external managed authentication and PostgreSQL service.
- Do not change production Supabase data or authentication settings as part of this infrastructure task.

## Acceptance criteria

- [ ] The V1 Azure resources are created in the shared resource group and carry consistent project/version/environment tags.
- [ ] NSG rules expose only required ports; SSH is restricted to the administrator's current public IP.
- [ ] Nginx serves the pinned frontend build over HTTPS.
- [ ] Nginx proxies the required TinyFish API paths to the Azure Function App over HTTPS.
- [ ] Adapted Azure Functions validate Supabase sessions and the required employee/role permissions.
- [ ] TinyFish credentials remain server-side and are not present in the browser bundle or public repository.
- [ ] Supabase login and required Togetherly application flows work.
- [ ] TinyFish search, fetch, agent, and agent-run routes are tested.
- [ ] Function timeout, hosting limits, and expected request duration are verified for the selected hosting plan.
- [ ] Resource configuration, tests, cost notes, known gaps, and sanitised evidence are documented.
- [ ] A teardown procedure is documented and tested without deleting the shared resource group or resources belonging to other versions.

## Known risks and open decisions

- The Vercel-style API handlers need an Azure Functions adapter and compatibility tests.
- The Functions hosting plan and region must support the application's request duration at an acceptable cost.
- The Nginx-to-Functions proxy must preserve paths, methods, headers, query strings, and response codes.
- The exact DNS and HTTPS certificate approach is not yet selected.
- Azure service availability and student subscription restrictions must be checked before provisioning.
