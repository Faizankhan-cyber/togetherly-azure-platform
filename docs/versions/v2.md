## V2 objective

Strengthen the existing Togetherly V1 VM-hosted application by removing the TinyFish API credential from the VM's application environment file, using a system-assigned Managed Identity to retrieve it from Azure Key Vault, restricting Key Vault network access, and adding resource-group-level tag governance.

V2 extends the V1 hosting architecture. It does not replace the VM with Azure Functions or introduce a new application hosting platform.

## Implemented controls

### 1. System-assigned Managed Identity

- Enabled system-assigned Managed Identity on `vm-togetherly-v1`.
- Used the VM identity as the workload identity for Key Vault access.
- No client secret or stored service-principal credential is required by the VM for this Key Vault retrieval path.

### 2. Azure Key Vault

- Created Key Vault `togetherly-key-2026` in Central India, Standard tier.
- Enabled soft delete with 90-day retention.
- Enabled purge protection.
- Selected the Azure RBAC permission model.
- Stored the TinyFish credential as secret `TINYFISH-API-KEY`.
- The secret value is intentionally excluded from source control, screenshots and this document.

### 3. Least-privilege role assignments

| Principal | Role | Scope | Purpose |
|---|---|---|---|
| VM system-assigned Managed Identity | Key Vault Secrets User | Key Vault | Read secret values required by the application |
| Authorised operator account | Key Vault Secrets Officer | Key Vault | Manage Key Vault secrets during administration |

The two assignments above are the intended V2 Key Vault roles. Existing subscription-level Owner assignments were inherited and were not changed as part of V2.

### 4. Key Vault network restrictions

- Public network access was changed from unrestricted access to selected network/IP access.
- The application VNet `vnet-togetherly-platform` and subnet `snet-app` were selected.
- The `Microsoft.KeyVault` service endpoint was enabled on `snet-app`.
- An administrator public IP allow-list entry was configured as a single-address rule. The actual address is deliberately not published.
- The VM successfully retrieved the secret after the network restrictions were applied.
- **No Key Vault Private Endpoint was deployed.** The vault uses its public endpoint with network ACL restrictions and the VNet service endpoint path.

The administrator IP allow-list entry may need updating if the administrator's public IP changes. Keep the actual address private.

### 5. Node.js Key Vault integration

The Node.js Express API uses the Azure SDK:

- `@azure/identity` with `DefaultAzureCredential`.
- `@azure/keyvault-secrets` with `SecretClient`.
- Vault endpoint: `https://togetherly-key-2026.vault.azure.net/`.
- Secret name: `TINYFISH-API-KEY`.
- Secret retrieval is cached in process memory for five minutes.
- Errors log the error name rather than the secret value.
- The TinyFish Search, Fetch, Agent start and Agent status routes call the shared secret helper rather than reading `process.env.TINYFISH_API_KEY`.
- The TinyFish API key was removed from the VM's application `.env` file.

The Supabase URL and publishable/anonymous key remain application configuration. They are not substitutes for a Supabase service-role key. A service-role key was not added to the VM as part of this V2 work.

### 6. Azure Policy governance

- Assigned the built-in **Require a tag and its value on resources** policy at the `rg-togetherly-platform` scope.
- Assignment name: `V2-Require-Project-Tag-Togetherly`.
- Parameter values: tag name `Project`, tag value `Togetherly`.
- Assignment enforcement mode: **DoNotEnforce**.
- The policy definition's effect is Deny, but the assignment's DoNotEnforce setting means this assignment evaluates compliance without blocking create/update operations.
- A resource-group policy state scan reported **8 of 8 resources compliant** and **0 non-compliant** at the time of verification.

This is an audit-style evaluation for this assignment, not an enforced deployment guardrail. It is also not a complete security benchmark.

## V2 architecture and request flow

See [V2 architecture](../architecture/v2-architecture.md) for the component diagram, trust boundaries and request flows.

1. A user accesses the Togetherly frontend over HTTPS.
2. Nginx serves the frontend and reverse-proxies TinyFish API requests to the Node.js Express service on loopback port 3001.
3. The API validates the user's Supabase bearer token and employee/role access through the existing application authentication flow.
4. When a TinyFish route needs the provider credential, the API uses the VM's system-assigned Managed Identity through `DefaultAzureCredential`.
5. The API reads `TINYFISH-API-KEY` from Key Vault over the permitted VNet service-endpoint network path.
6. The API calls TinyFish from the server side and returns the application response to the authenticated user.
7. Supabase remains the external authentication and application data service.

The browser does not need the TinyFish API key. The application API is intended to remain bound to loopback and is reached through Nginx.

## Security review and residual risks

- The Key Vault endpoint is public, with network ACL restrictions. It is not a Private Endpoint deployment.
- The administrator IP allow-list entry can become stale when the public IP changes.
- Key Vault Secrets Officer is a powerful secret-management role; keep it limited to the authorised operator and review assignments periodically.
- The VM still has a public web endpoint for HTTPS. Keep NSG rules narrow and SSH restricted to a trusted administrator source.
- The system-assigned identity is scoped to the VM. Review any future role assignments before adding permissions.
- The tag policy uses DoNotEnforce and does not prevent non-compliant resource creation.
- The inherited subscription Owner assignments were observed but not modified. Review them separately in the subscription IAM blade.
- This is a learning-project security review, not a penetration test, formal compliance attestation or independent audit.

**Key Vault warning:** `togetherly-key-2026` has soft delete enabled with 90-day retention and purge protection enabled. Deleting its resource group does not mean the soft-deleted vault is immediately purged. Its name may remain unavailable during the retention period, and purge protection prevents early permanent deletion. The Bicep rebuild must account for this, for example by using a new versioned vault name. Do not disable or bypass recovery protections just to reuse a name.

**Teardown status:** Resource-group deletion is confirmed by the owner. This does not independently confirm that no orphaned resources remain outside the group or that all delayed billing has settled. Check Azure Resource Groups, Disks, Public IPs, Snapshots, deleted Key Vaults and Cost Management after data refresh.

## Cost and operational review

See [V2 cost and operations review](../runbooks/v2-cost-and-operations-review.md).

- The VM is the primary ongoing compute cost while running. Deallocate it when not needed for testing.
- Deallocation does not remove managed-disk charges and may not remove public IP charges.
- Key Vault may incur charges based on vault tier and operations. Avoid unnecessary secret polling and do not create a Private Endpoint unless its cost is approved.
- Managed Identity, RBAC assignments, a service endpoint and Azure Policy assignment do not require a separate always-on VM.
- Verify current Azure Cost Management actuals and forecast in the subscription; no billing amount or credit balance is published in this repository.
