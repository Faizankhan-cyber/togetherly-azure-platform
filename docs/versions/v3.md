# V3 — Cloud Hardening and Operations

**Status:** Planned  
**Certification milestone:** Planned after AZ-104.  
**Learning alignment:** AZ-104  
**Infrastructure method:** Azure Bicep. Terraform is not used in this project.

Planned focus: network hardening, Azure Monitor, Log Analytics, actionable alerts, backup and tested restore, VM patching, maintenance, and operational runbooks.

## First task: rebuild the V1 and V2 baseline

Recreate V1 and V2 from source-controlled Bicep templates before adding any new V3 change. Validate each template with a what-if run before deploying. Parameters must not contain secrets. The soft-deleted V2 Key Vault name may be unavailable, so use a new versioned vault name; do not disable recovery protections to reuse a name. See the [V1/V2 Infrastructure Preservation Pack](../preservation/v2-infrastructure-preservation-pack.md).

## Deferred from V2

These items were excluded from V2 and are planned for V3. None of them is implemented, and none may be represented as deployed until it is verified with evidence.

- Azure Bicep templates and automated deployment (the rebuild above).
- GitHub Actions OIDC federation to Azure, so CI/CD needs no stored Azure credential.
- Key Vault Private Endpoint. Approve the cost before deploying it.
- Azure Monitor alerting and Log Analytics (also part of the V3 focus above).
- Microsoft Sentinel: V3 covers enabling the workspace and connecting data sources. KQL detection rules and incident investigation remain in V4.
- Security testing of the project-owned environment. This is a controlled self-test, not a formal penetration test or external compliance certification.

Azure Functions is not planned. The backend stays on the VM.

## Rules

Record actual recovery and operational results; do not claim controls based only on configuration intent. Define data ingestion, retention, permissions and cost before enabling paid or high-volume services. Test only project-owned or explicitly authorised systems.
